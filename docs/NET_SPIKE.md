# M0 联机 Spike 报告

## 传输层

- `Transport` 在建房成功后返回房间码。加入操作等到对端可收发后完成。调用方按对端 ID 和通道发送 JSON 兼容消息，通过类型化事件接收对端加入、离开、消息、断开和错误。每个实例负责一场连接会话，离开后可新建实例。发送统计记录提交次数，交付以接收端统计为准。
- 两种实现均采用星型拓扑。客户端只与房主通信，房主为每个客户端保留独立连接，最多接入 5 个客户端。房间码采用配置字母表中的 4 个字符。PeerJS 注册 `bblitz-` 加房间码，收到 `unavailable-id` 就更换房间码，最多尝试 5 次。
- `LocalTransport` 使用按房间隔离的 `BroadcastChannel`。消息带发送方和接收方 ID，房主逐个确认加入并拒绝满房请求。支持 Web Locks 的浏览器会在同一来源内保留房间码，直到房主离开。正常离开会主动通知。双方每秒检查并发送心跳，超过 5 秒未收到对端心跳或数据就清理连接。该模式适用于同源、同浏览器存储分区内的标签页。
- `PeerJsTransport` 使用 PeerJS 公共信令、Google STUN 和 `TURN_SERVERS` 配置。客户端使用本地生成的 UUID 注册信令 ID，再分别发起 `reliable` 和 `unreliable` 两条 JSON `DataConnection`。双方以可靠通道交换就绪帧后才公布对端。每帧 UTF-8 编码后须小于 16,300 字节，字节数包含传输封装。连接建立最多等待 10 秒。任意一条通道关闭都会清理整对通道。ICE 中断有 5 秒恢复窗口，信令断开会单独报告。
- 弱网包装器给本端发出的数据增加 150 ms 延迟，并以 5% 概率在 `unreliable` 发送前丢弃消息。两端都开启时，可靠 ping/pong 的 RTT 预计增加约 300 ms。此开关模拟应用层提交行为，WebRTC 原生重传参数由浏览器另行报告。

诊断入口为 `/block-blitz/?spike=net`。加上 `&net=local` 切换本地模式。分享链接保留当前路径与模式，`&room=XXXX` 预填房间码，打开链接后点击「加入房间」。页面支持两通道手动发送、各连发 100 条、手动与定时 RTT 和有界日志。每个对端最多保留 16 个在途 RTT 探测，按 ID 匹配，10 秒后过期。正常游戏的 `/#/room/XXXX` 邀请流程属于后续大厅功能。

## 浏览器实测

2026-11-24，Windows 的 Electron 44.10.1（Chromium 152.0.7977.169），通过 Vite Preview 加载生产构建。所有标签页在同一台机器上，PeerJS 使用公共信令 `0.peerjs.com`，依赖锁定为 **PeerJS 1.5.5**。下列数值是该次试验的样本。

### PeerJS 双通道

| 页面通道 | PeerJS 选项 | 实测 `ordered` | 实测 `maxRetransmits` | 实测 `maxPacketLifeTime` |
| --- | --- | --- | --- | --- |
| `reliable` | `reliable: true` | `true` | `null` | `null` |
| `unreliable` | `reliable: false` | `false` | `null` | `null` |

房主和客户端显示相同的参数。房主信令 WebSocket 创建至收到 `OPEN` 用时约 960 ms，点击建房至显示房间码约 994 ms。客户端点击加入至双通道就绪约 1,885 ms。客户端的两条连接均进入 `connected`，选中的 ICE 候选对均为 `host → host`。房主和客户端的 RTT 样本分别为 0.9 ms 和 0.7 ms。

双方各在每条通道发送一条文本和 100 条序号消息。两端每条通道均提交并接收 101 条，序号消息各收到 100/100，观察到的乱序和重复均为 0。连发结果反映同机连接，`ordered` 属性直接来自浏览器的 `RTCDataChannel`。

让第二个房主首次尝试注册已占用的 `bblitz-R4VP`，公共信令返回 `ID-TAKEN`。随后更换房间码为 `GCVE`，收到 `OPEN`，建房成功。

客户端主动离开后房主移除对端。客户端再次加入后，房主主动断开，客户端清空对端列表并提示连接已断开。

### LocalTransport

在同一浏览器分区打开房主和两个客户端，两个分享链接均正确预填房间码。建房用时约 29 ms，两个客户端加入约 12 ms 和 11 ms。房主看到两个客户端，两个客户端分别只看到房主。

- 未开启弱网的房主和客户端双向各发送一条文本和 100 条序号消息。双方每条通道各收到 101 条，最近一轮序号均为 100/100，乱序和重复为 0。客户端 RTT 样本为 0.6 ms。
- 第二个客户端开启弱网后各提交 100 条。房主收到 `reliable` 100/100、`unreliable` 96/100，该客户端 RTT 样本为 150.5 ms。另一个客户端未收到这轮消息。
- 第一个客户端导航离开诊断页后，房主列表从两个对端减为一个。随后房主主动断开，剩余客户端收到断开事件并清空列表。

诊断页在 390×844 与 844×390 两种 CSS 视口下均可滚到日志，无横向溢出，可见按钮最小高度为 44 CSS px。两种模式的复制按钮向 Clipboard API 提交了包含 `/block-blitz/` 的完整分享 URL，使用测试替身捕获调用参数。

## 与 GDD 的差异及 M2 处理建议

GDD §8.5 计划将输入和快照放在无序、不可靠的通道。PeerJS 1.5.5 将 `reliable` 映射到 `createDataChannel` 的 `ordered`，两个重传限制均保留为 `null`，因此这里的 `unreliable` 实际采用无序可靠传输。Spike 保留 GDD 的通道名称，用实测参数明确其行为。

M2 可以先保留现有实现，用序号或 tick 丢弃过期状态，并控制待发送队列，避免积压旧快照。应用层丢弃无法取消底层已经发生的重传。若跨网络压测要求发送后不重传，可通过 `Transport` 增加原生 WebRTC 实现，使用 `ordered: false, maxRetransmits: 0`，同时验证消息大小、浏览器兼容性和断线行为。

## 已知风险与回退

| 风险 | 回退或处置 |
| --- | --- |
| 公共信令不可用或异常断开 | 同机开发使用 `&net=local`。跨网部署可评估自建 PeerServer 或 Trystero 信令。信令断开时，已打开的 WebRTC 通道可能继续可用。 |
| 4G、对称 NAT 或企业网络打洞失败 | 先由电脑家宽建房，记录失败阶段，再用 Wi-Fi 对照。持续无法直连时评估 TURN，目前 `TURN_SERVERS` 为空。 |
| 房主离开或房间满 | 房主离开会结束房间。Local 满房直接提示，PeerJS 满房会关闭超额握手，客户端可能等到连接超时。 |
| 浏览器冻结后台标签页或长时间限流定时器 | Local 心跳可能暂停并触发超时。回到前台后，从诊断页重新建房或加入。 |
| 两条独立 WebRTC 连接增加 ICE 协商和资源开销 | M2 多客户端测试记录建连时间、失败率、RTT 与拥塞情况，再决定是否在一个 `RTCPeerConnection` 上协商两条通道。 |

## M0-4 电脑 + 手机 4G 真机验收

待 GitHub Pages 部署本次代码后执行。同机实测尚未覆盖运营商网络、跨设备打洞、TURN 或手机原生浏览器。可从 [Pages 诊断入口](https://daoguang1012.github.io/block-blitz/?spike=net) 打开。

1. 电脑连家宽并打开诊断入口，确认是 PeerJS 模式。点击「创建房间」，记建房用时和房间码，复制分享链接。
2. 手机关闭 Wi-Fi，确认使用 4G。用手机浏览器打开分享链接，核对预填房间码后点「加入房间」。记录结果、耗时和错误原文。连接后在竖屏和横屏分别确认可滚动到日志。
3. 两端分别手动发送 `reliable` 和 `unreliable` 文本，各点一次连发和「测量 RTT」。等计数稳定，再记录两端接收条数、乱序、重复、两通道原生参数和 RTT。
4. 手机点「断开连接」，确认电脑移除对端。手机重连后由电脑断开，确认手机显示断线。若加入失败，先保留 4G 原始结果，再切 Wi-Fi 重试作对照。
